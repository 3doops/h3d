# HotA 3D: Godot-клиент поверх оригинальной игры

Оригинальная Heroes 3 HotA (`h3hota.exe`, SoD + HotA.dll) работает как **сервер механики**: путь, очки хода,
посещения, бои, ИИ, диалоги считает движок. Мост `bridge/bridge.py` (Frida-агент в процессе игры) отдаёт
состояние по WebSocket (JSON, `PROTOCOL.md`) и передаёт команды. **Godot-клиент** (`client/`, Godot 4.7.2,
Forward+) только рисует 3D-мир и шлёт ввод игрока. Правил игры в клиенте нет.

```
ВМ 10.10.0.108 (Windows, session 0, без GPU)               ПК пользователя (есть видеокарта)
┌─────────────────────────────────────────────┐            ┌──────────────────────────────────┐
│ game\Heroes3_HotA1\h3hota.exe (скрыто)      │            │ HotA3D.exe (экспорт)             │
│   └─ Frida: снимок, команды, диалоги, бои   │            │   или godot/client в редакторе   │
│ godot/bridge/bridge.py  ws://…:8765  ───────┼── JSON ───►│ 3D-рельеф, модели, герои, HUD    │
│                                    ◄────────┼─ команды ──│ клики, путь, «конец хода»        │
└─────────────────────────────────────────────┘ WebSocket  └──────────────────────────────────┘
```

На ВМ клиент рисует на CPU (Mesa lavapipe) — около 0,4 кадра/с, годится только для скриншотов. Играть —
клиентом на своём ПК с видеокартой (нужен Vulkan).

**Статус (2026-10-18): прототип работает.** Итог и доказательства — раздел «Итог прототипа» ниже,
`godot/out/final/`.

## Репозиторий, ассеты, релизы

- **Код** — этот репозиторий, [3doops/h3d](https://github.com/3doops/h3d). В проекте реверс-инжиниринга
  (h3-regress) он подключён submodule'ом в `godot/`, поэтому пути в документации записаны как `godot/...`.
- **Модели и текстуры** — [3doops/h3d-assets](https://github.com/3doops/h3d-assets), submodule в `client/assets`,
  файлы хранятся в Git LFS. Как менять модели — `client/assets/README.md`.
- **Сборки** — [Releases](https://github.com/3doops/h3d/releases): каждый коммит в `main` собирает Windows x64 и
  Linux x86_64 (`.github/workflows/release.yml`, тот же `tools/export_client.sh`) и выпускает версию с номером
  патча на 1 больше предыдущей (первая 1.0.0). Номер минорной или мажорной версии меняется тегом вручную
  (`git tag v1.1.0 && git push origin v1.1.0`), дальше счёт продолжится от него.

```sh
git lfs install                                          # один раз
git clone --recursive https://github.com/3doops/h3d.git  # код + ассеты
git submodule update --init                              # если клонировали без --recursive
```

Пока `h3d-assets` закрытый, сборке в Actions нужен секрет `ASSETS_TOKEN` в настройках h3d: fine-grained токен
с правом Contents: read на h3d-assets.

Отдельно от h3-regress работают клиент, мост и экспорт: `tools/export_client.sh` берёт пути из окружения (`DL`,
`DIST`, `GODOT`, см. шапку скрипта). Конвейеру моделей `assets3d/` и скриптам `shot.sh` и `e2e.sh` нужна раскладка
h3-regress: распакованные ресурсы `assets/h3-original/`, игра `game/`, Godot и lavapipe в `_dl/`.

## Что умеет

- **Мир от движка:** снимок карты (почвы, реки, дороги, два уровня, туман войны), 1233 объекта тестовой карты
  3D-моделями (`assets3d/`, чего нет — процедурные заглушки по категориям), герои с флагами, города, ресурсы и дата.
  Дальше — изменения (`state`): объекты, туман, ресурсы, армии, дата.
- **Ход героя считает движок:** клик по клетке — путь движка (зелёный — дойдёт сегодня, красный — позже), второй
  клик — ход; анимация по событию `hero_move`, камера ведёт героя. Посещения (ресурсы, сундуки, шахты, жилища…)
  выполняет движок, HUD показывает новые ресурсы и пишет изменения в журнал.
- **Диалоги движка** (`NormalDialog`: сундук, события карты, «герои ещё могут ходить», повышение уровня) — панель
  клиента, ответ уходит в игру; нет ответа — движок берёт ответ по умолчанию.
- **Окна движка, которых клиент не рисует** — сквозной показ: город, найм, экран героя, рынок, таверна, обмен,
  обзор королевства, окна HotA. Мост шлёт кадры окна (JPEG), клиент показывает их поверх затемнённого мира, мышь и
  клавиши уходят в игру. Открыть — кнопки у городов и героев в HUD или войти героем в свой город.
- **Бои:** по умолчанию быстрый бой движка (итог в журнале); с `bridge.py --battles manual` — ручной бой на экране
  боя движка тем же сквозным окном (кнопки боя, «автобой»).
- **Конец хода:** ходы ИИ в движке (видимые ходы ИИ клиент анимирует), новый день, доход.
- **Главное меню игры, любой режим** (`bridge.py --menu`, по умолчанию в локальном режиме): клиент начинает с
  настоящего главного меню HotA на весь экран — новая игра (сценарий, случайная карта, кампания, обучение, hot-seat),
  загрузка, рекорды, титры, выход; как только игра вошла на карту, клиент строит 3D-мир, вышла — снова меню
  (раздел «Как играть»).
- **Локальный режим:** клиент сам находит оригинальную игру, проверяет, всё ли есть (чек-лист с подсказками),
  запускает игру + мост на этом ПК и закрывает их при выходе; на Linux — игра и мост под Wine (раздел 0).
- **Оригинальная игра рядом, играть в обоих окнах** (`bridge.py --visible`, PLAN 4.6; в локальном режиме — по
  умолчанию, если есть рабочий стол, галка «Окно игры на экране» в панели F3): окно HotA открыто на рабочем столе;
  что сделано в Godot, видно в оригинале (герой идёт, ресурсы, диалоги и окна — в окне игры), а то, что игрок сделал
  в окне игры (повёл героя, подобрал, ответил на диалог, вошёл в город, закончил ход, вышел в меню), клиент
  повторяет. На диалог можно ответить с любой стороны.
- Подключение к удалённому мосту по сети (`--url`, панель адреса F2, SSH-туннель); сборки под Windows x64 и Linux x86_64.

## Как играть: с главного меню, как в оригинале

Локальный режим (раздел 0) запускает игру с её **главного меню**; на ВМ то же даёт `bridge.py --menu`. Клиент
показывает экран игры целиком (с полями по краям, пропорции сохранены), мышь и клавиатура идут в игру — меню
работает как в оригинале:

- **Новая игра** → «Один игрок» (выбор сценария, «Случайная карта», дополнительные опции, сложность), «Кампания»,
  «Обучение», «Несколько игроков» → «Один компьютер» (hot-seat, имена игроков). **Загрузить игру**, **Рекорды**,
  **Создатели**, **Выход**.
- Вступление сценария и «Ходит красный» показывает ещё экран игры; после OK клиент переходит к 3D-карте (строится по
  снимку от движка; на CPU-рендере это минуты, на видеокарте — секунды).
- На карте: кнопка **«Меню игры»** в HUD (или **Esc**) — системные опции игры поверх мира: сохранить, загрузить,
  начать заново, главное меню, выход из игры, настройки (скорость, «Быстрая битва», звук). «Главное меню» и
  «Загрузить» возвращают экран меню; загруженная или новая игра — новый 3D-мир. «Выход из игры» закрывает игру, мост и
  (в локальном режиме) через 3 секунды клиент.
- **Бои — как в игре:** опция «Быстрая битва» в системных опциях. Выключена — экран боя игры поверх мира (свои
  действия, «автобой», отступление…), включена — быстрый бой; итоги боя закрываете сами.
- **Hot-seat:** клиент показывает мир глазами игрока, чей сейчас ход (туман, герои, ресурсы); сообщение «Ходит …» —
  панель диалога.
- **Сетевая игра** (IPX, TCP/IP, модем, прямое соединение, онлайн) недоступна — игра отвечает сообщением: DirectPlay
  в этой сборке отключён (игра работает без рабочего стола).

## 0. Локальный режим: игра на этом же ПК

### Linux: быстрый старт

1. Поставить Wine (это единственное, что нужно ставить; Python уже в пакете):
   - Debian/Ubuntu: `sudo dpkg --add-architecture i386 && sudo apt update && sudo apt install wine wine32 wine64`
   - Fedora: `sudo dnf install wine`
   - Arch: включить `[multilib]` в `/etc/pacman.conf`, затем `sudo pacman -S wine`
2. `tar xzf HotA3D-client-linux-x86_64.tar.gz && cd HotA3D-client-linux-x86_64`
3. `./run.sh` — клиент ищет игру; не нашёл — сразу открывает выбор папки: указать папку с `h3hota.exe`
   (Heroes 3 Complete + HotA 1.8.0). Выбор запоминается. Первый запуск создаёт свой префикс Wine
   `~/.local/share/HotA3D/wine` (около минуты), затем стартуют игра и мост, клиент показывает мир.

`./doctor.sh` — проверка из консоли, строки `[ OK ]` / `[WARN]` / `[FAIL]` с подсказкой: Wine есть и его версия;
Wine запускает `python/python.exe` из пакета с frida + websockets (`wine python.exe -c "import frida, websockets"`);
файлы игры; порт 8765 свободен. С `python3` на хосте это полный `bridge/doctor.py` (ещё 32-битные программы в Wine,
версия игры, DISPLAY); без `python3` — те же основные пункты на sh (клиент тоже обходится без `python3`).

**Frida под Wine здесь не проверялась** (на ВМ нет Linux/WSL): пакет собран и мост из `python/` проверен на Windows
с настоящей игрой; под Wine — только имитация проверок. Не стартует — журнал
`~/.local/share/godot/app_userdata/HotA 3D Client/local_run/bridge.log`.

**Свой Python в пакете (оба пакета).** `python/` = официальный embeddable-zip python.org 3.12.10 (64 бит) +
колёса win_amd64 `frida 17.23.3`, `websockets 13.1`, `Pillow` (запасной JPEG), распакованные в `Lib/site-packages`;
`python312._pth` перечисляет `Lib\site-packages` и `..\bridge` (в режиме `._pth` папка скрипта сама в `sys.path` не
попадает). 64-битный Python с frida ставит агент в 32-битную `h3hota.exe` (так работает и системный на ВМ).
Windows: берётся системный Python, если в нём есть frida + websockets, иначе `python\python.exe`. Linux:
`wine python/python.exe bridge.py`. Сборка — `godot/tools/make_bridge_python.py` из `_dl/bridge-python/`
(embeddable-zip и `wheels/`, скачиваются `pip download --platform win_amd64 --only-binary=:all:`).

**Префикс Wine (Linux).** По умолчанию — свой: `~/.local/share/HotA3D/wine` (win64, 32-битные программы через WoW64;
создаётся `wineboot -i` без диалогов Mono/Gecko). Даже если игра лежит в другом префиксе (`~/.wine`, Lutris, Bottles,
Proton) — её папка запускается как есть через `Z:` в своём префиксе: HotA не нужен реестр установщика (настройки окна
и звука мост ставит сам), чужой префикс не меняется, версия Wine/Proton того префикса не важна. Переопределить:
`WINEPREFIX=… ./run.sh` (тогда этот префикс) или `HOTA3D_WINE_PYTHON=/путь/python.exe` (свой Windows-Python; тогда,
как раньше, префикс игры или `~/.wine`, и frida нужна в нём).

### Как устроено

Клиент сам запускает оригинальную игру и мост на своей машине — отдельно поднимать `bridge.py` не нужно.
Включается, когда клиент запущен без `--url`/`--server` и режим «локальный» (при первом запуске — локальный, если в
панели F2 ещё не сохранён адрес), или явно: `--local`, `--game-dir ПАПКА`, кнопка «Игра на этом ПК…» в панели F2.
Обратно — «Удалённый мост…» в панели F3 или ввод адреса в F2. Выбор режима и папки — в `user://local.cfg`
(Windows: `%APPDATA%\Godot\app_userdata\HotA 3D Client\`, Linux: `~/.local/share/godot/app_userdata/HotA 3D Client/`).

```
HotA3D.exe                                         # локальный режим: найти игру → проверка → игра + мост → мир
HotA3D.exe --local --game-dir "D:\Games\HoMM 3 Complete"   # явно (папка запоминается)
HotA3D.exe --url ws://10.10.0.108:8765             # удалённый мост (локальный режим не включается)
python godot/bridge/doctor.py                      # та же проверка из консоли (в пакетах: bridge/doctor.py, ./doctor.sh)
```

**Где игра.** Порядок: сохранённая папка → `--game-dir` → переменная `HOTA_GAME_DIR` → копия репозитория
(`game\Heroes3_HotA1`) → поиск `doctor.py`: Windows — реестр (`AppPath` Heroes 3, GOG id 1207658787), `X:\GOG Games\…`,
`Program Files (x86)\GOG Galaxy\Games\…`, `3DO\Heroes 3`, Steam `common`, подпапки `Games`/`Program Files` с `h3hota.exe`;
Linux — префиксы Wine (`$WINEPREFIX`, `~/.wine`, `~/.local/share/wineprefixes/*`, Lutris `~/Games/*`, Bottles,
Steam/Proton `compatdata/*/pfx`) с теми же путями внутри `drive_c` и их `system.reg`. Годная папка — та, где есть
`h3hota.exe`, `HotA.dll`, `Data/H3bitmap.lod`, `Data/H3sprite.lod`, `Data/HotA.lod` (регистр букв не важен). Не нашлась
или не годится — панель (F3) пишет, каких файлов нет, и кнопка **«Папка игры…»** открывает выбор папки (системный
диалог, где он есть); выбор запоминается. Сверка версии: хеши `h3hota.exe`/`HotA.dll` HotA 1.8.0, с которыми сделан
мост; другие — предупреждение (адреса движка зависят от сборки).

**Проверка («чего не хватает»).** Перед запуском клиент запускает `bridge/doctor.py --json` и показывает чек-лист
(✓ / ! / ✘, у каждого ✘ — одна строка «как исправить»), то же пишет в консоль (`HotA3D.console.exe`):

| Пункт | Windows | Linux |
|---|---|---|
| ОС, папка игры, файлы, версия | ✓ | ✓ |
| файлы моста (`bridge/` рядом с клиентом) | ✓ | ✓ |
| интерпретатор | Python 3.8+ (ищет `py -3`, `python`, `%LOCALAPPDATA%\Programs\Python\Python3*`, `HOTA3D_PYTHON`; берёт тот, где уже есть frida, иначе `python\python.exe` из пакета) | `python3` хоста — только для `doctor.py`; нет — клиент проверяет сам |
| frida ≥ 17, websockets ≥ 13 | в этом Python (в `python\` пакета — уже есть) | в Windows-Python под Wine: `python/python.exe` пакета (уже есть) |
| Wine | — | `wine` в PATH и версия (подсказка по дистрибутиву: apt / dnf / pacman / zypper) |
| префикс | — | `WINEPREFIX`, иначе свой `~/.local/share/HotA3D/wine` (создаётся сам); со своим `HOTA3D_WINE_PYTHON` — префикс игры или `~/.wine`; win64/win32; Proton — предупреждение |
| 32-битные программы | — | `wine C:\windows\syswow64\cmd.exe /c echo` (нет — `apt install wine32` или Wine 9+ WoW64) |
| Windows-Python под Wine | — | `HOTA3D_WINE_PYTHON` → `python/python.exe` пакета → установленный в префиксе (`drive_c/users/*/AppData/Local/Programs/Python/Python3*`, `Program Files`, `C:\Python3*`); `wine python.exe -c probe` |
| реестр | HKLM доступен? иначе — HKCU VirtualStore (предупреждение) | — |
| порт | 8765 свободен? иначе — следующий свободный | то же |
| игра уже запущена | предупреждение | предупреждение |
| DISPLAY | — | нужен графический сеанс |

**Запуск и остановка.** Всё в порядке → клиент запускает команду, которую вернул `doctor.py`, и подключается к
`ws://127.0.0.1:ПОРТ`: Windows — `python -I bridge/bridge.py --game-dir … --port … --control-dir … --log …`; Linux —
`WINEPREFIX=… wine …/python.exe -I Z:\…\bridge.py --game-dir C:\… …` (пути переводятся в пути Wine: `drive_c` → `C:`,
остальное — `Z:`). Связь с мостом — файлы в `user://local_run/`: `status.json` (мост пишет `starting → game → ready`,
`error` с текстом, `game_pid`), `stop` (клиент просит выйти: мост закрывает игру и возвращает настройки реестра),
`heartbeat` (клиент обновляет раз в 5 с; если клиент упал, мост выходит через 15 мин), `bridge.log`. При выходе
клиент создаёт `stop`, ждёт до 8 с, затем убивает мост и игру по `game_pid` (`taskkill`, под Wine — `wine taskkill`).
Окно самой игры (800×600): `doctor.py --visible auto` (по умолчанию) — на рабочем столе оно открыто, и в нём можно
играть одновременно с клиентом (мост `--visible`, PLAN 4.6), его можно и свернуть — игра не останавливается; без
рабочего стола (служба, session 0) или с галкой «Окно игры на экране» выключенной — игра идёт скрыто (окно создаётся
без `WS_VISIBLE`). Галка в панели F3 (`user://local.cfg` `[local] game_window = auto|on|off`, флаг клиента
`--game-window on|off|auto`) применяется при следующем запуске моста.
Настройки игры в реестре (окно, без звука, `Autosave=0`, быстрый бой) мост ставит на время работы и **возвращает**
прежние при выходе.

**Linux: почему так.** Игра — 32-битная Windows-программа, поэтому только под Wine. Frida должна работать внутри
этого Windows-процесса, а сам `bridge.py` пользуется Windows API (`winreg`, GDI+ в `frames.py`, `MapVirtualKeyW`).
Выбран путь (а): **Windows-Python с frida и websockets в том же префиксе Wine**, `wine python.exe bridge.py`: Frida
для Windows ставит агент штатным для Windows способом (CreateProcess suspended + инъекция), всё остальное в мосту не
меняется, а WebSocket-порт Wine — обычный порт хоста. Отброшено: (б) Linux-frida, цепляющаяся к процессу Wine —
она видит ELF-процесс `wine-preloader`, не знает PE-модулей и соглашений вызова Windows (агенты ищут функции
`kernel32`/`user32`, ставят C-хуки с `stdcall/thiscall`), а мосту всё равно нужен Windows API; (в) `frida-server.exe`
под Wine + Linux-Python с удалённым устройством — тот же риск инъекции под Wine плюс правка Windows-зависимого кода моста.
**На настоящем Linux это не запускалось** (на ВМ нет ни Linux, ни WSL): логика поиска, проверок и команды запуска
проверена имитацией (`python -I godot/bridge/test_doctor.py`: поддельные `~/.wine`, Lutris, Proton, `system.reg`,
ответы `wine`/`python.exe`). Возможные проблемы: инъекция Frida под Wine (если `frida.spawn` падает — сообщить
`bridge.log`), JPEG через gdiplus Wine (`frames.py` откатится на Pillow/PNG).

Подготовка Linux — только Wine (см. «Linux: быстрый старт» выше); Windows-Python ставить в префикс больше не нужно.

Требования Python (`bridge/requirements.txt`): `frida>=17` (проверено 17.23.3), `websockets>=13` (13.1), Python 3.8+
(проверено 3.12.10, 64 бит).

## 1. На ВМ: игра + мост

```
python -I godot/bridge/bridge.py --host 0.0.0.0        # запустить игру (GODOT_TEST.GM1) и мост для сети
python -I godot/bridge/bridge.py --host 0.0.0.0 --menu # игра с главного меню: игрок сам выбирает режим
python -I godot/bridge/bridge.py                       # только 127.0.0.1 — для SSH-туннеля (безопаснее)
```

| Флаг | Что |
|---|---|
| `--host 0.0.0.0` / `--port N` | слушать сеть (по умолчанию 127.0.0.1:8765) |
| `--load X.GM1` | другое сохранение из `game\Heroes3_HotA1\games\` (тест боя: `GODOT_BATTLE.GM1`) |
| `--menu` | начать с главного меню игры (вместо `--load`): любой режим выбирает игрок; бои по умолчанию `--battles game` |
| `--visible` | окно игры на рабочем столе (по умолчанию скрыто): играть и в нём, и в клиенте; диалоги в обоих, изменения из окна игры → `state` `why: external` (PLAN 4.6) |
| `--game-dir DIR` | другая папка игры (по умолчанию `HOTA_GAME_DIR`, иначе `game\Heroes3_HotA1`) |
| `--control-dir DIR` / `--log FILE` | локальный режим: `status.json`, `stop`, `heartbeat` (раздел 0), журнал в файл |
| `--battles manual` | бои человека — на экране боя движка (сквозное окно у клиента); по умолчанию быстрый бой (`auto`); `game` — как скажет опция игры «Быстрая битва» (по умолчанию с `--menu`) |
| `--attach` | к уже запущенной игре (`launch.py --keep`); `--keep-game` — не закрывать игру при выходе |
| `--dialog-timeout SEC` | сколько движок ждёт ответа на диалог (120 с), потом ответ по умолчанию |
| `--record DIR` | записать снимки и трафик |
| `--mock` / `--mock --replay godot/bridge/testdata/snapshot_newcomers.json` | без игры: синтетическая карта / записанный снимок |

Правила для окон движка (`--windows`), частота кадров окон (`--fps`) и прочее — в `bridge/README.md`.
Python с `frida` и `websockets`: `C:\Users\dev0\AppData\Local\Programs\Python\Python312\python.exe`.
Игра одна на ВМ; запускать из сессии агента / SSH (session 0).

У моста **нет пароля**: `--host 0.0.0.0` — только в доверенной сети (и никогда вместе с `--debug`). Порт в
брандмауэре ВМ (PowerShell от администратора):
`New-NetFirewallRule -DisplayName "HotA3D bridge" -Direction Inbound -Protocol TCP -LocalPort 8765 -Action Allow`.

## 2. На своём ПК: клиент

**Готовая сборка** — `dist/HotA3D-client-win64.zip` или `dist/HotA3D-client-linux-x86_64.tar.gz` (собираются
`bash godot/tools/export_client.sh [linux]`): распаковать и запустить. Внутри, кроме клиента, — `bridge/` (исходники
моста, агенты Frida, `doctor.py`, `requirements.txt`, тестовые сохранения) и `python/` (свой Windows-Python с frida,
websockets, Pillow) для локального режима (раздел 0) и `README.txt`. Мало места на диске: `export_client.sh linux --pck-from-win` — без экспорта Godot, `HotA3D.pck` и `python/` берутся потоком из zip Windows (pck не зависит от платформы, пресеты одинаковы). Linux: `./run.sh`, `./doctor.sh`; нужен Vulkan (`vulkaninfo --summary`), без него Godot переходит на
OpenGL 3.3 — так клиент не проверялся.

```
HotA3D.exe                                  # панель «Подключение к мосту»: ввести адрес, Enter (запоминается)
HotA3D.exe --url ws://10.10.0.108:8765      # сразу к ВМ по сети (мост с --host 0.0.0.0)
HotA3D.exe --url ws://127.0.0.1:8765        # через SSH-туннель (см. ниже)
HotA3D.console.exe --url …                  # то же с консолью: журнал клиента
```

Адрес можно писать коротко (`10.10.0.108` → `ws://10.10.0.108:8765`). Панель сама появляется, когда нет связи;
**F2** — открыть её в любой момент (сменить мост). Остальные флаги клиента (`--cam`, `--level`, `--fast` …) —
после `--`, см. `client/README.md`.

**SSH-туннель** — если до ВМ доступен только SSH (мост остаётся на 127.0.0.1):

```
ssh -N -L 8765:127.0.0.1:8765 dev0@10.10.0.108     # держать открытым, клиент — на ws://127.0.0.1:8765
```

**Из редактора** — открыть `godot/client/project.godot` в Godot 4.7.2 (обычная сборка, не .NET) и F5; адрес —
в панели или в *Project → Project Settings → Run → Main Run Args* (`--url ws://10.10.0.108:8765`). Модели и
текстуры клиент читает сам во время работы, импорт редактора им не нужен: в `client/assets/models/` и
`client/assets/terrain/` лежат `.gdignore`, иначе первое открытие импортирует ~540 GLB (~340 МБ) много минут.
Экспортировать — только `tools/export_client.sh` (он кладёт GLB/JPEG в `.pck` без изменений; экспорт из
редактора их не включит).

## 3. Управление

ЛКМ по клетке — путь от движка (зелёный — дойдёт сегодня, красный — позже), повторный клик — идти; ЛКМ по своему
герою или кнопка в списке — выбор. ПКМ-тащить — поворот, СКМ-тащить / WASD / стрелки — сдвиг, колесо / Z X —
масштаб, Q E — поворот, R F — наклон. Tab / PgUp / PgDn — поверхность/подземелье, Пробел — к герою, G — сетка,
Enter — конец хода (или OK в диалоге), Esc — сбросить путь, если он показан, иначе системные опции игры (как
кнопка «Меню игры»), H — скрыть HUD, F2 — адрес моста, F3 — панель локального режима.

Экран меню игры (главное меню, выбор сценария, загрузка…): мышь и все клавиши, кроме F2/F3, — в игру.

Окна игры: кнопка с башенкой у города / со шлемом у героя в списках HUD (или войти героем в свой город) — окно
движка поверх мира; мышь и клавиши над ним идут в игру (координаты 800×600), закрывает его сама игра (её кнопка,
Esc или ✕ в заголовке). Ручной бой (`--battles manual`) открывается так же, при нападении.

## 4. Что пока не так

- Окна движка (город, герой, рынок, бой…) — картинка 800×600 с кликами, а не свои 3D-экраны (этап 5). Клик во
  время анимации или хода врага в бою движок отбрасывает, как настоящий; курсор движка в кадр не попадает.
- Бой — быстрый бой движка или ручной на экране боя движка; 3D-бой — этап 5.
- Модели есть примерно для трети каталога (~330 из 956 + леса), остальное — процедурные заглушки по категориям;
  партии генерируются фоном (`assets3d/README.md`).
- Ход ИИ не прерывается: команды во время хода ИИ ждут. Одна игра и один клиент-игрок на мост.
- Видимая игра (`--visible`): проверена в session 0 этой ВМ (стиль окна, ввод сообщениями окну, всё зеркало —
  `test_client.py --scenario mirror`), но **картинку в окне на настоящем рабочем столе никто не видел**: вывод через
  GDI в session 0 не проходит (станция окон невидима), на Windows-ПК и под Wine — не проверено. Ходьба в окне игры
  анимирована: клиент получает её несколькими `hero_move`; выбор героя в окне игры клиент повторяет, путь (стрелки)
  — нет. Оба игрока на одном ходу — это один игрок: hot-seat «два человека в двух окнах» не сделан.
- Сетевая игра недоступна (DirectPlay заглушён). Hot-seat: между ходами людей клиент не прячет мир предыдущего
  игрока, пока тот не нажал OK в «Ходит …» (снимок нового игрока приходит после этого сообщения).
- Мост на Frida (без пароля); своя DLL — этап 5. Локальный режим проверен на Windows (эта ВМ); на Linux (Wine) —
  только имитацией, на настоящем Linux не запускался. Сборка Linux не запускалась вовсе (проверено: ELF x86-64, права).
- Экспортированный `HotA3D.exe` на Mesa lavapipe упал при выходе (segfault после работы и кадра, 2026-10-18,
  `export_client.sh --test`); на ПК с видеокартой не проверялось.

## 5. Сборка, скриншоты, видео

```
bash godot/tools/export_client.sh            # dist/HotA3D-client-win64.zip (exe + pck + bridge/; папка после проверки
                                             #   zip удаляется — места мало; --keep-dir оставляет dist/HotA3D-client/)
bash godot/tools/export_client.sh linux      # dist/HotA3D-client-linux-x86_64.tar.gz (+ run.sh, doctor.sh, bridge/)
python -I godot/bridge/test_doctor.py        # проверка поиска игры и чек-листа (в т. ч. имитация Linux/Wine)
bash godot/tools/export_client.sh --test     # + запуск экспорта здесь на lavapipe против bridge.py --mock --replay
bash godot/tools/shot.sh -o real -r -R godot/bridge/testdata/snapshot_newcomers.json   # кадр из редакторной сборки
bash godot/tools/shot.sh -o demo -a -v 40 -s 1280x720                                    # видео авто-сценария (мок)
bash godot/tools/e2e.sh main [-v 20] [-o DIR]   # игра + мост + клиент --auto: кадры, отчёт, журнал моста [+ видео]
bash godot/tools/e2e.sh battle                  # то же на GODOT_BATTLE.GM1 с ручным боем
```

`e2e.sh` сам запускает и закрывает игру (`h3hota.exe` на ВМ одна), сценарий окон города задан координатами окна
движка 800×600 для этого сохранения. Без видео прогон идёт ~20 мин, с видео 20 к/с — около часа (CPU, ~3 с на кадр).

Шаблоны экспорта 4.7.2 — `_dl/godot-templates-4.7.2/` (`tools/fetch_export_templates.py --platform windows|linux`
вынимает из официального `.tpz` только нужную платформу, сверяя SHA-512; сам `.tpz` не сохраняется).
Скриншоты и видео — `godot/out/`: **`final/`** (итог, см. выше), `real/` (первый сценарий на настоящем движке,
`real_auto.mp4`), `pt/` (окна движка в клиенте), `auto_*.png`, `coast1.png`, `export_test.png` (экспортированный
клиент против `bridge.py --mock --replay`), `bridge/` (кадры самого движка из `test_client.py`).
